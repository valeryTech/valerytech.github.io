# Analytics

The production site uses Google Analytics 4 with measurement ID
`G-XF1V06CDS3`. It can also load PostHog and Microsoft Clarity when their public
project identifiers are configured. Analytics is not loaded by local
development builds.

## What the site sends

GA4 sends a `page_view` for every page load. Each page view includes GA4's
standard page URL, page title, referrer, traffic-source, campaign, device, and
approximate-location data. The site also sets GA4's standard `content_group`
parameter to the top-level Hugo section, such as `engineering` or `ai`.

Every PostHog page view and custom event includes content context generated by
Hugo: page path and title, page kind, section, content type, depth, tags, word
count, reading time, publication and modification dates, and the deployed Git
revision.

The local analytics code adds these stable events:

- `internal_navigation` records a move from one site page to another. It sends
  `source_path`, `destination_path`, and `navigation_area`. Navigation areas
  distinguish content links, section navigation, the table of contents,
  breadcrumbs, previous/next links, search results, and site navigation.
- `reader_engaged` is sent once when the page has been visible for at least 10
  seconds, the visitor has interacted with it, and at least 25 percent of the
  page has been visible. This is a useful quality signal, not proof that the
  visitor is human.
- `reading_summary` records active and elapsed seconds, maximum scroll depth,
  interaction count, engagement, and completion when the page is left.
- `toc_navigation` records same-page heading navigation.
- `outbound_navigation` records only the destination host and a fixed category,
  such as reference, social, repository, AI tool, or contact.
- `search_opened`, `search_completed`, and `search_result_selected` record
  search outcomes, result counts, and result positions without search text.
- `copy_requested`, `resource_downloaded`, and
  `display_preference_changed` record the corresponding site controls.
- `not_found_viewed` records requests handled by the custom 404 page.

The code deliberately does not send complete referrer URLs, search terms,
copied content, contact addresses, or other user-entered data as custom
parameters. URL query strings and fragments are removed from PostHog URL
properties. Standard UTM properties remain available for acquisition reports.

The same custom events are forwarded to PostHog and Clarity when those services
are enabled. PostHog supplies web and product analytics, including page paths,
sources, autocaptured interactions, heatmaps, dead and rage clicks, Web Vitals,
browser exceptions, and bot/AI traffic classification. It keeps a pseudonymous
browser identifier for return-visit analysis, but does not create person
profiles and respects Do Not Track. PostHog session recording is disabled
because Clarity owns replay.

Clarity starts with both analytics and advertising storage consent denied. It
can collect limited cookieless activity, but multi-page session continuity is
reduced until a future consent mechanism grants analytics storage.

## Enable PostHog and Clarity on GitHub Pages

The identifiers are public browser configuration, not credentials. Store them
as GitHub **repository variables**, not secrets, under **Settings > Secrets and
variables > Actions > Variables**:

| GitHub variable         | Value                                                      |
| ----------------------- | ---------------------------------------------------------- |
| `POSTHOG_PROJECT_TOKEN` | Project token from PostHog project settings                |
| `POSTHOG_HOST`          | `https://us.i.posthog.com` or the EU host shown by PostHog |
| `POSTHOG_PROJECT_ID`    | Numeric project ID used only for source-map upload         |
| `CLARITY_PROJECT_ID`    | Project ID from Clarity **Settings > Overview**            |

Readable production error stacks require one GitHub Actions secret:

| GitHub secret         | Value                                                      |
| --------------------- | ---------------------------------------------------------- |
| `POSTHOG_CLI_API_KEY` | Personal API key restricted to error-tracking write access |

The source-map step is fail-open, so an upload outage does not block the site
deployment. Source maps are deleted before the GitHub Pages artifact is
uploaded and the personal API key is never included in the website.

The deployment workflow maps those values to Hugo configuration. A provider is
omitted completely when its identifier is empty. Pull-request builds do not use
the production repository variables.

For a one-off Docker production build with both providers enabled:

```sh
HUGOxPARAMSxANALYTICSxPOSTHOGTOKEN=phc_example \
HUGOxPARAMSxANALYTICSxPOSTHOGHOST=https://us.i.posthog.com \
HUGOxPARAMSxANALYTICSxCLARITYID=example \
make build
```

The build wrapper forwards these variables into the Docker container. The
pinned container remains the supported local toolchain.

Before enabling the GitHub variables:

1. In PostHog, confirm the project region and keep session replay disabled for
   this project. Bot and AI traffic classification is applied in web analytics
   at query time.
2. In Clarity, keep bot detection enabled. In **Settings > Setup**, turn off
   cookies by default so the denied consent signal and project setting agree.
3. In both products, set data retention to an appropriate period and restrict
   project access.
4. Review the published privacy page after deployment.

## PostHog dashboards and goals

Create four saved dashboards:

- **Content**: pageviews, engaged-reader rate, completion rate, active reading
  time, second-page sessions, and top entry and exit pages.
- **Discovery**: the search-open to result-selection funnel, no-result rate,
  internal paths, navigation areas, copy actions, and downloads.
- **Acquisition quality**: channel, referrer, UTM, country, device, and browser
  broken down by engagement and completion. Use PostHog's bot and AI filters.
- **Technical health**: p75 LCP, CLS, and INP by page and device; exceptions by
  release and page; dead and rage clicks; and missing paths.

Pin `reader_engaged` and `reading_summary` filtered to `completed = true` as the
primary goals. Treat search-result selection, copy/download actions, and useful
outbound categories as secondary goals.

## GA4 property setup

The following settings require Editor access to the GA4 property and cannot be
stored in this repository.

1. Open **Admin > Data streams > Web** and select `valery.tech`.
2. Turn on Enhanced measurement. Keep page views, scrolls, outbound clicks,
   and file downloads enabled. Page views must include page loads.
3. Open **Admin > Data display > Custom definitions** and add these
   event-scoped custom dimensions:

   | Dimension name   | Event parameter    |
   | ---------------- | ------------------ |
   | Destination path | `destination_path` |
   | Navigation area  | `navigation_area`  |
   | Source path      | `source_path`      |

   GA4 already has standard dimensions for page path and content group, so do
   not create duplicates for those.

4. In **Admin > Data collection and modification > Data retention**, choose a
   retention period that covers the desired exploration window.
5. If regular visits from the site owner distort the data, define internal
   traffic for the relevant IP addresses. Put the internal-traffic data filter
   in **Testing** mode before making it active because active filters are not
   retroactive and discarded events cannot be restored.

New custom dimensions usually take 24 to 48 hours to appear in reports. They do
not backfill events collected before the dimensions were created.

## Verify after deployment

Use **Reports > Realtime** for the first smoke test:

1. Visit a production page in a browser without an analytics blocker.
2. Follow an internal link to a different page.
3. Confirm that both pages appear and that `internal_navigation` is listed.
4. Stay on a page for 10 seconds and scroll or interact with it. Confirm that
   `reader_engaged` is listed.
5. Inspect `internal_navigation` and confirm the source, destination, and area
   parameters have the expected values.

Use DebugView only for targeted testing. Do not enable debug mode for normal
production visitors.

## Reports to use

For page-level statistics, open **Reports > Engagement > Pages and screens** and
change the primary dimension to **Page path and screen class**. Add **Content
group** when comparing top-level sections.

For page-to-page movement, create a **Path exploration** with page path as the
node type. A free-form exploration of the `internal_navigation` event can show
source path, destination path, and navigation area in one table.

For acquisition, use **Reports > Acquisition > Traffic acquisition**. Prefer
session-scoped dimensions such as **Session source / medium** when asking where
a visit began. Add UTM parameters to links controlled by the site owner, for
example:

```text
https://valery.tech/ai/?utm_source=linkedin&utm_medium=social&utm_campaign=ai_notes
```

Do not place names, email addresses, or other personal information in UTM
values.

## Investigate suspected bot traffic

GA4 automatically removes bots that it recognizes, but no client-side
analytics system catches every automated browser. Country or city alone is not
evidence of automation. VPN exits, corporate proxies, data centers, and
privacy services can all make human visits appear to come from Singapore.

Create a free-form exploration filtered to **Country = Singapore**. Compare:

- landing page and session source / medium;
- browser, operating system, device category, and screen resolution;
- engaged sessions and average engagement time;
- `reader_engaged` users;
- `internal_navigation` events and destinations;
- bursts of nearly identical visits over short time windows.

A large cluster with the same environment, one landing page, almost no active
time, no reader engagement, and no internal navigation is suspicious. It is
still not conclusive because GA4 discards IP addresses and does not provide the
network owner or autonomous system number.

To confirm bot traffic, put an edge service with request analytics in front of
GitHub Pages. Cloudflare is one option. Edge data can see requests that never
run JavaScript and can compare source networks, user agents, request rates, and
bot classifications. That infrastructure change should be evaluated
separately from browser analytics.

## Behavior analytics responsibilities

The three configured browser tools have separate jobs:

- GA4 is the acquisition and reporting baseline.
- PostHog provides flexible paths, autocaptured behavior, and bot/AI traffic
  classification.
- Microsoft Clarity provides session inspection, heatmaps, intent signals, and
  its own bot filtering.

Session replay records substantially more behavior than aggregate analytics.
The privacy notice therefore names Clarity explicitly. Input values remain
masked, storage consent starts denied, and the PostHog recorder remains off.
