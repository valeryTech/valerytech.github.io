> **An evaluation system is not attached to a model, prompt, or feature. It is attached to the product behavior covered by a commitment—so teams can swap models, rewrite prompts, and change architecture while knowing what users can actually rely on.**

An AI product's behavior comes from the whole configured system: models, prompts, retrieval, tools, permissions, state, and UI. Unit and integration tests establish whether code mechanisms and hard safeguards work; evaluation examines recorded whole-system behavior in defined situations so product managers and engineers can make grounded decisions. ([Huyen 2025](#huyen-2025))

## Discovery and delivery use evaluation differently


[Discovery and delivery]({{< ref "ai/product/operating-model/discovery-and-delivery" >}}) are concurrent kinds of work distinguished by their purpose and obligations, not sequential project phases:

| Dimension | Discovery (*build to learn*) | Delivery (*build to earn*) |
| --- | --- | --- |
| **Main question** | What happens, where does this approach break, and is our assumption plausible enough for the next step? | Can users rely on this bounded behavior across supported situations as models, prompts, and data change? |
| **Role of variance** | Helpful when exploring alternatives and exposing unexpected failure surfaces | Operational risk that must be bounded by code controls or measured across repeated runs |
| **Evaluation basis** | Provisional claims and domain judgment applied directly to traces | Explicit [production commitments]({{< ref "ai/product/operating-model/production-commitment" >}}), hard code invariants, and criteria with pre-set required levels |
| **Typical setup** | 10–25 purposeful cases or live probes, full trace capture, manual review by PM/domain owner and engineer | Held-out comparison and regression sets, 3–5 repeats per case, calibrated code checks and narrow LLM judges, CI and live sampling |
| **When a check fails** | Revise the problem framing, narrow the candidate workflow, fix an ambiguous prompt, or drop the option | Fix the implementation, block or roll back the change, tighten a runtime gate, or narrow the commitment |

Crossing from an exploratory prototype into behavior that real users or systems depend on is a **commitment gate**, regardless of whether the code lives in a notebook or a production repo. Any live test that can affect real users or records requires a bounded commitment—supported scope, hard safety gates, observation, and a way to stop or undo it—sized to its blast radius.

## Start with the smallest useful pass


Do not build an evaluation platform, a 500-case dataset, or automated LLM judges before inspecting real behavior:

1. **Name the decision and next commitment.** Write down what choice waits on this evaluation (e.g., *commit two weeks to a retrieval redesign*, or *open an internal pilot to 25 users*) and what could go wrong if you guess badly.
2. **Split hard gates from measured claims.** Put rules that must hold *every time* (permissions, confirmation before writes, schema validity, idempotency) into application code and unit-test them; reserve evaluation for behavior that code alone cannot decide.
3. **Assemble 10–20 purposeful cases with real fixtures.** Include clear baseline requests, ambiguous or missing inputs, multi-step state, and boundary conditions where a failure hurts.
4. **Run the complete system and capture full traces.** Log versions, inputs, fixtures, retrieved context, tool calls and payloads, state before/after, latency, and cost—not just the final chat reply.
5. **Read the traces together.** Have the PM or domain expert and engineer inspect every trace, separate prompt/spec bugs (fix immediately) from generalization failures, and check whether the intended behavior itself makes sense.
6. **Write a scoped finding, then decide.** Record what passed, what failed, what evidence was missing (`NOT JUDGEABLE`), and what remains unknown—keeping the finding separate from the product decision.

Scale repeatability—larger datasets, repeated runs for spread, calibrated LLM judges, release gates, and production sampling—only as repeated comparisons and bigger commitments demand it.
