**Type-driven design**, **designing with types**, and **domain modeling with types** use the type system as a software-design tool: modeling states, APIs, workflows, errors, invariants, boundaries, and state transitions.

## The core idea


A value moves from a weaker type to a stronger one once something about it has been established:

```text
string → Email
string → UserId
number → PositiveQuantity
DTO → ValidatedOrder
AnonymousUser → AuthenticatedUser
DraftOrder → SubmittedOrder
SubmittedOrder → PaidOrder
```


The type records **what has already happened and what operations are legal now**.

An analogy is the documents you collect at an airport. Check-in gives you a boarding pass, security stamps it, and the gate asks only for the stamped pass, not for your booking, your passport and proof that you went through security. Each document is evidence that a step happened, and it's what makes the next step possible. `DraftOrder -> SubmittedOrder -> PaidOrder` works the same way: you can edit only a draft and refund only a paid order, and the compiler plays the gate agent. Modeling such transitions is the subject of [Workflows And States]({{< ref "type-driven-design/workflows-and-states" >}}).

This is the software-design use of typed programming.

The recurring idea is:

```text
untrusted / weakly typed value
          │
          │ runtime computation establishes P(x)
          ▼
   value carrying evidence of P
          │
          │ static type checker preserves
          │ that evidence through the program
          ▼
     domain computation
```


Scala's `opaque type + smart constructor` is a relatively lightweight version of this idea. Refinement and dependent type systems push more of `P(x)` itself into what the compiler can reason about.

## Costs and failure modes


The approach has costs, and it can go wrong: conversion code at every boundary, types that lie because something constructs them without checking, facts that expire after they're checked, modeling too precisely before the domain is understood, and encodings harder to read than the invariant they protect. These are worked through, with sources, in [What Belongs In Types]({{< ref "type-driven-design/what-belongs-in-types" >}}#costs-and-failure-modes); the guard against most of them is the [What Belongs In Types]({{< ref "type-driven-design/what-belongs-in-types" >}}#rule-of-thumb).

## Notes in this section


In suggested reading order:

**Foundations**

1. [Type systems]({{< ref "type-driven-design/type-systems" >}}): what a type system proves and how (soundness, conservativity), the dimensions (static, dynamic and gradual checking; safety; nominal and structural equivalence), benefits, inference, and types as propositions.
2. [What belongs in the type system]({{< ref "type-driven-design/what-belongs-in-types" >}}): types, contracts, runtime checks and tests; which properties make good targets; a decision procedure; where types stop matching reality; costs and failure modes.

**Modeling**

3. [Parse, don't validate]({{< ref "type-driven-design/parse-dont-validate" >}}): partial functions made total, where to parse, and how strong a parsed type's evidence is (constructive and encapsulated types, hidden constructors, ghosts of departed proofs).
4. [Domain modeling with types]({{< ref "type-driven-design/domain-modeling-with-types" >}}): product and sum types, sums versus hierarchies, primitive obsession, making illegal states unrepresentable, values and entities, errors as values.
5. [Workflows and states]({{< ref "type-driven-design/workflows-and-states" >}}): workflows as function types, one type per state, state machines, typestate with phantom types, and type-first design.
6. [Types at the boundary]({{< ref "type-driven-design/types-at-the-boundary" >}}): trust boundaries, DTOs and serialization, the database as a boundary, evolving types, and tolerant readers.

**Architecture**

7. [Functional domain modeling]({{< ref "type-driven-design/functional-domain-modeling" >}}): Ghosh's principles, keeping effects out of the domain, modules as algebras with laws, composing effectful operations, commands and events.
8. [Effects, interpreters and wiring]({{< ref "type-driven-design/effects-and-interpreters" >}}): Reader and Kleisli, tagless final, free monads, ZIO, algebraic effects, and embedded DSLs.

**Further**

9. [Refinement and dependent types]({{< ref "type-driven-design/refinement-and-dependent-types" >}}): predicates in types, how the checking works, support by language, limits, and the progression towards dependent types.
10. [Scala type system]({{< ref "type-driven-design/scala-type-system" >}}): abstract types and the currency case study, nominal and structural subtyping, union and intersection types, path-dependent types, type tags, multiversal equality, and encoding contracts in Scala.
11. [Declarative design]({{< ref "type-driven-design/declarative-design" >}}): declarative specifications and engines, four senses of "declarative", DSLs, DDD, and semantic modeling.
12. [Reading paths]({{< ref "type-driven-design/reading-paths" >}}): a map of every source with where it's held, and curricula for practical type-driven design, runtime checks and type evidence, and type theory.
