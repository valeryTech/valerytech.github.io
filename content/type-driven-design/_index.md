**Type-driven design**, **designing with types**, and **domain modeling with types** use the type system as a software-design tool: modeling states, APIs, workflows, errors, invariants, boundaries, and state transitions.

## The core idea


A value moves from a weaker type to a stronger one once something about it has been established:

```text
string → Email
string → UserId
number → PositiveQuantity
DTO → ValidatedOrder
AnonymousUser → AuthenticatedUser
DraftOrder → SubmittedOrder
SubmittedOrder → PaidOrder
```


The type records **what has already happened and what operations are legal now**.

An analogy is the documents you collect at an airport. Check-in gives you a boarding pass, security stamps it, and the gate asks only for the stamped pass, not for your booking, your passport and proof that you went through security. Each document is evidence that a step happened, and it's what makes the next step possible. `DraftOrder -> SubmittedOrder -> PaidOrder` works the same way: you can edit only a draft and refund only a paid order, and the compiler plays the gate agent. Modeling such transitions is the subject of [Workflows And States]({{< ref "type-driven-design/03-domain-modeling/workflows-and-states" >}}).

This is the software-design use of typed programming.

The recurring idea is:

```text
untrusted / weakly typed value
          │
          │ runtime computation establishes P(x)
          ▼
   value carrying evidence of P
          │
          │ static type checker preserves
          │ that evidence through the program
          ▼
     domain computation
```


Scala's `opaque type + smart constructor` is a relatively lightweight version of this idea. Refinement and dependent type systems push more of `P(x)` itself into what the compiler can reason about.

## Costs and failure modes


The approach has costs, and it can go wrong: conversion code at every boundary, types that lie because something constructs them without checking, facts that expire after they're checked, modeling too precisely before the domain is understood, and encodings harder to read than the invariant they protect. These are worked through, with sources, in [What Belongs In Types]({{< ref "type-driven-design/01-foundations/what-belongs-in-types" >}}#costs-and-failure-modes); the guard against most of them is the [What Belongs In Types]({{< ref "type-driven-design/01-foundations/what-belongs-in-types" >}}#rule-of-thumb).
